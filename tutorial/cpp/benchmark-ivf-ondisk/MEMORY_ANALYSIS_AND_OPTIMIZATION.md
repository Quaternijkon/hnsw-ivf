## 发现的问题与优化

### 问题1：Groundtruth 数据计入内存监控 ⚠️（已修复）

**原始问题**：
- Groundtruth 数据在内存监控期间加载（第383行）
- 虽然 groundtruth 不是搜索本身需要的，但会被计入搜索阶段内存
- 对于大数据集，groundtruth 可能占用一定内存

**修复**：
- ✅ 将 groundtruth 加载移到内存监控停止之后
- ✅ 确保搜索阶段内存只反映实际搜索操作的内存占用
- ✅ 提前删除索引对象，释放内存

**修复前**：
```cpp
// 记录搜索阶段峰值内存
result.search_memory_mb = search_memory_monitor.getPeakMemoryMB();

// 计算召回率（在内存监控期间加载groundtruth）
vector<vector<int32_t>> groundtruth = read_ivecs(GROUNDTRUTH_FILE);
delete index;
```

**修复后**：
```cpp
// 记录搜索阶段峰值内存
result.search_memory_mb = search_memory_monitor.getPeakMemoryMB();

// 停止内存监控
search_memory_monitor.stop();

// 提前删除索引释放内存
delete index;

// 计算召回率（在内存监控停止后）
vector<vector<int32_t>> groundtruth = read_ivecs(GROUNDTRUTH_FILE);
```

## MMAP 的实际行为与限制

### Faiss mmap 的实现细节

虽然使用了 `IO_FLAG_MMAP`，但 Faiss 的 mmap 实现可能仍会将某些部分加载到内存：

### 1. **量化器（IndexFlatL2）可能被完全加载**

**原因**：
- 量化器在搜索时需要频繁随机访问（每个查询都要找到最近的聚类中心）
- Faiss 为了性能，可能将量化器完全加载到内存
- 量化器大小：`nlist × d × 4字节`

**内存占用估算**：
- nlist=1000, d=128: ~512KB（很小）
- nlist=10000, d=128: ~5MB（较小）
- nlist=100000, d=128: ~51MB（较大）

### 2. **索引元数据会被加载**

**包括**：
- 倒排列表的索引表
- 向量计数信息
- 其他元数据结构

**内存占用**：通常较小（<10MB）

### 3. **访问的倒排列表按需加载**

**按需加载**：
- 根据 `nprobe`，访问 `nprobe` 个倒排列表
- 每个列表的大小取决于该聚类的向量数量
- 只有被访问的列表才会真正占用物理内存

**内存占用估算**：
- 对于均匀分布的100万向量：
  - nlist=1000, nprobe=10: 访问约1%的数据 = ~5MB
  - nlist=1000, nprobe=100: 访问约10%的数据 = ~50MB
  - nlist=10000, nprobe=100: 访问约1%的数据 = ~5MB

## 内存占用组成分析

### 搜索阶段内存占用

**使用 mmap 后的内存组成**：

1. **量化器**（可能完全加载）
   - IndexFlatL2: ~0.5-50MB（取决于nlist）
   - 这部分可能无法通过 mmap 优化

2. **索引元数据**（会被加载）
   - 倒排列表索引表等: ~1-10MB
   - 这部分也可能被完全加载

3. **访问的倒排列表**（按需加载）✅
   - 根据 nprobe 访问的部分: ~5-200MB（取决于nprobe）
   - 这部分通过 mmap 按需加载，节省内存

4. **查询数据**
   - 10,000个查询: ~5MB

5. **搜索结果**
   - 10,000 × 10 × (4+4)字节: ~0.8MB

**总内存占用估算**：

| nlist | nprobe | 量化器 | 元数据 | 倒排列表 | 查询+结果 | **总计** |
|-------|--------|--------|--------|----------|-----------|----------|
| 1000  | 10     | 0.5MB  | 2MB    | ~5MB     | ~6MB      | **~13MB** |
| 1000  | 100    | 0.5MB  | 2MB    | ~50MB    | ~6MB      | **~58MB** |
| 10000 | 10     | 5MB    | 5MB    | ~5MB     | ~6MB      | **~21MB** |
| 10000 | 100    | 5MB    | 5MB    | ~50MB    | ~6MB      | **~66MB** |

### 为什么可能仍然较高？

如果实际测量到的内存占用远高于上述估算，可能的原因：

1. **量化器被完全加载**
   - Faiss 可能为了性能将量化器完全加载
   - 对于大的 nlist，这可能占用较多内存

2. **操作系统页面缓存**
   - mmap 映射的文件可能被操作系统缓存
   - 多次访问后，页面可能仍在内存中

3. **内存碎片化**
   - 多次分配/释放可能导致内存碎片
   - 实际占用可能高于实际数据大小

4. **Faiss 内部缓存**
   - Faiss 可能在内部缓存某些数据结构
   - 这可能导致额外的内存占用

## 总结

### ✅ 已完成的优化

1. ✅ **Groundtruth 数据延迟加载**：不在内存监控期间加载
2. ✅ **提前删除索引**：在加载 groundtruth 之前删除索引对象
3. ✅ **停止内存监控**：确保后续操作不计入搜索阶段内存

### ⚠️ MMAP 的限制

即使使用了 mmap，以下部分仍可能被完全加载到内存：
- **量化器**：可能为了性能被完全加载
- **索引元数据**：通常会被加载
- **频繁访问的页面**：操作系统可能缓存页面

### 📊 预期内存占用

对于典型的 IVF 索引：
- **最小情况**（nlist=1000, nprobe=10）：~10-20MB
- **典型情况**（nlist=1000, nprobe=100）：~50-100MB
- **最大情况**（nlist=10000, nprobe=1000）：~200-500MB

**注意**：如果实际占用远高于此，可能是：
1. 量化器被完全加载（取决于 nlist）
2. 操作系统页面缓存
3. 内存碎片化
4. Faiss 内部缓存

### 🎯 建议

如果内存占用仍然很高，可以：
1. **检查 nlist 大小**：较大的 nlist 会导致量化器占用更多内存
2. **检查 nprobe 大小**：较大的 nprobe 会访问更多倒排列表
3. **使用系统工具监控**：`top` 或 `htop` 查看实际物理内存占用
4. **检查页面缓存**：`free -h` 查看系统内存使用情况
